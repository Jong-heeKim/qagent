# 문제가설 도출 (5WHY 기법)

**서비스**: AI Agent 품질 측정 플랫폼  
**참조**: 관찰결과, 체험결과, 고객경험인터뷰결과, 유저저니맵  
**분석 방법**: 5WHY 기법 + 다층적 근본원인 분석

## 현상문제 3개 및 5WHY 분석

| 현상문제 | WHY1 | WHY2 | WHY3 | WHY4 | WHY5 | 근본원인 |
|---------|------|------|------|------|------|----------|
| **AI Agent 품질 측정 환경 구성에 수일~수주가 소요되며, 비기술 직군(PM·기획자·운영자)은 시작조차 못 한다** | 왜 측정 환경 구성에 수일~수주가 걸리고 비기술 직군은 시작하지 못하는가? → 라이브러리 설치·버전 충돌 해결·테스트셋 수작업·IT팀 의뢰 대기 등 기술 선행 작업이 필수이기 때문이다 | 왜 복잡한 기술 선행 작업이 반드시 필요한가? → 모든 LLM 평가 도구가 CLI·코드 기반 개발자 전용으로 설계되어 있고, No-Code 대안이 전혀 없기 때문이다 | 왜 도구가 개발자 전용으로만 설계되었는가? → LLM 평가 시장이 연구자·ML엔지니어를 주 사용자로 형성되어, 비기술 직군의 수요가 제품 설계에 반영되지 않았기 때문이다 | 왜 비기술 직군의 수요가 도구 설계에 반영되지 않았는가? → 조직 내 AI 품질 관리 책임이 엔지니어링 팀에만 귀속되어 있고, PM·기획자가 품질 의사결정에 참여하는 구조 자체가 없기 때문이다 | 왜 AI 품질 의사결정 구조가 엔지니어 팀에만 귀속되는가? → AI Agent 품질이 비즈니스 성과와 직결된다는 인식이 조직 전체에 없고, 비기술 직군이 품질을 이해할 언어(지표·기준·시각화)가 제공되지 않기 때문이다 | **AI 품질 관리가 기술 직군에만 귀속된 조직 구조적 폐쇄성**<br>· 기술적: No-Code 평가 환경 부재, 개발자 전용 도구 생태계<br>· 심리적: 엔지니어의 "품질=기술 영역" 인식, 비기술 직군의 기술 진입 두려움<br>· 제도/시스템적: 품질 관리 책임 집중, 비기술 참여 프로세스 부재<br>· 맥락적: LLM 평가 시장 초기, 비기술 도구 생태계 미성숙<br>· 커뮤니케이션: 기술 지표를 비기술 언어로 번역하는 체계 부재 |
| **측정 결과 수치가 도출되어도 그것이 좋은지 나쁜지 판단할 기준이 없어 의사결정에 활용되지 못한다** | 왜 수치가 나와도 좋은지 나쁜지 판단하지 못하는가? → 업계 표준 벤치마크·도메인별 기준치·이전 버전 대비 히스토리가 없기 때문이다 | 왜 업계 표준 벤치마크와 기준치가 없는가? → LLM 평가 지표(Faithfulness·Context Recall 등)가 학술 연구에서 파생되어, 실무에서 합의된 "충분한 수준"이 아직 형성되지 않았기 때문이다 | 왜 학술 지표가 실무 기준으로 자리잡지 못했는가? → 의료·금융·이커머스 등 도메인마다 요구 품질 수준이 달라(의료 99%+ vs 이커머스 80% 허용) 보편적 기준 단일화가 불가능하기 때문이다 | 왜 도메인별 기준조차 없는가? → AI Agent를 실서비스로 운영하는 기업들이 내부 품질 기준을 경쟁적 자산으로 간주하여 공개하지 않고, 업계 공유 체계가 없기 때문이다 | 왜 업계 차원의 품질 기준 공유·표준화가 이루어지지 않는가? → AI Agent 품질 관리를 비즈니스 리스크로 인식하는 단계가 초기이며, 표준화를 주도할 플랫폼·제도적 주체(정부·협회·리딩 기업)가 없기 때문이다 | **AI Agent 품질 해석 생태계(기준·벤치마크·해석 가이드) 부재**<br>· 기술적: 평가 지표 해석 가이드 미제공, 시계열 히스토리 저장 기능 부재<br>· 심리적: 수치 해석 못하는 무기력감, "모른다"고 보고 못 하는 심리적 압박<br>· 제도/시스템적: 업계 품질 기준 표준화 기구 부재, 조직 내 AI 품질 KPI 미정의<br>· 맥락적: AI Agent 품질 관리 시장 미성숙, 학술-실무 간 지식 이전 지연<br>· 커뮤니케이션: 기술 지표를 경영진·비기술 직군 언어로 전환하는 해석 계층 없음 |
| **품질 개선 적용 후 효과를 검증하는 데 수주가 소요되어 빠른 반복 개선이 불가능하다** | 왜 품질 개선 효과 검증에 수주가 걸리는가? → 개선(프롬프트 수정·파라미터 변경·파인튜닝) 후 재측정을 위해 평가 환경 재구성·IT팀 의뢰 대기·결과 분석을 매번 처음부터 반복해야 하기 때문이다 | 왜 개선 후 재측정을 매번 처음부터 반복해야 하는가? → 버전별 품질 자동 비교·개선 전후 재평가·결과 추적을 지원하는 자동화 파이프라인이 없기 때문이다 | 왜 품질 측정-개선-재측정 파이프라인이 자동화되지 않았는가? → LLM의 비결정론적 특성·고비용 API 호출·느린 응답으로 인해 일반 CI/CD 패턴을 적용할 수 없고, LLM 특화 자동화 표준이 없기 때문이다 | 왜 LLM 특화 자동화 파이프라인 표준이 없는가? → LLM 평가는 문맥 이해·도메인 전문성·Human-in-the-Loop 판단이 필요하여 완전 자동화가 어렵고, 이를 해결한 상용 솔루션이 시장에서 검증되지 않았기 때문이다 | 왜 Human-in-the-Loop와 자동화를 결합한 파이프라인이 상용화되지 않았는가? → AI Agent 품질 개선이 비즈니스 핵심 KPI와 연결된다는 인식 부족으로 경영진·기술 리더의 투자 우선순위에서 밀리고, 투자를 정당화할 ROI 측정 방법 자체도 없기 때문이다 | **AI Agent 품질 개선-검증 자동화 생태계 부재 + 조직의 품질 투자 우선순위 미정립**<br>· 기술적: LLM 비결정론적 특성으로 표준 CI/CD 적용 불가, 버전 비교 자동화 도구 부재<br>· 심리적: 복수 변수 동시 변경으로 개선 원인 불명의 무력감<br>· 제도/시스템적: AI 품질 개선이 조직 KPI 미정의, 개선-검증 예산·인력 할당 없음<br>· 맥락적: 빠른 제품 개발 중심 문화에서 품질 관리 후순위, Shift-Left 품질 문화 미형성<br>· 커뮤니케이션: 개선 효과 보고 표준 포맷 부재로 개선 투자 승인 어려움 |

## 근본원인 요약

### 1. AI 품질 관리가 기술 직군에만 귀속된 조직 구조적 폐쇄성
- **핵심**: 측정 도구·환경이 개발자 전용으로 설계되어 비기술 직군은 품질 측정에 참여 불가
- **영향 범위**: 전체 사용자 — 특히 PM·기획자·운영자·팀장
- **WHY 사슬**: 기술 선행 작업 필수 → 개발자 전용 도구 설계 → 비기술 수요 미반영 → 엔지니어 독점 구조 → 조직 인식·언어 부재

### 2. AI Agent 품질 해석 생태계(기준·벤치마크·해석 가이드) 부재
- **핵심**: 측정은 가능하지만 결과가 의미하는 바를 아무도 해석할 수 없어 측정 자체가 무의미
- **영향 범위**: 기술직·비기술직 공통 — 측정 후 단계 전체 마비
- **WHY 사슬**: 기준치 없음 → 학술 지표의 실무 미정착 → 도메인 다양성 → 기업 기준 비공개 → 업계 표준화 주체 부재

### 3. AI Agent 품질 개선-검증 자동화 생태계 부재 + 조직 품질 투자 우선순위 미정립
- **핵심**: 개선-측정-검증 사이클이 수동으로 분절되어 빠른 반복 개선이 구조적으로 불가능
- **영향 범위**: 전체 사용자 — 개선 루프가 닫히지 않아 품질 향상 자체가 불가능
- **WHY 사슬**: 매번 재구성 반복 → 자동화 파이프라인 없음 → LLM 특화 CI/CD 불가 → 완전 자동화 어려움 → 품질 투자 ROI 측정 불가

```
       │                                    │
       └────────────────┬───────────────────┘
                        │  (측정해도 의미 없고, 개선해도 검증 불가)
                        ▼
              [문제3] 개선-검증 사이클 단절
                        │
                        ▼
           [결과] AI Agent 품질 관리 투자 포기 → 품질 저하 반복
```

> **공통 구조**: 세 근본원인은 모두 **"AI Agent 품질 관리 생태계 미성숙"** 이라는 공통 맥락을 가진다.  
> 서비스가 해결해야 할 핵심 과제는 단순 측정 도구 제공이 아닌, **접근성·해석 가능성·자동화 사이클** 을 동시에 제공하는 통합 품질 플랫폼이어야 함을 시사한다.
